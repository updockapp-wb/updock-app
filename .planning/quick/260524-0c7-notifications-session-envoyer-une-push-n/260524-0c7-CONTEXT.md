# Quick Task 260524-0c7: Notifications session — push sur création de session

**Gathered:** 2026-05-24
**Status:** Ready for planning

<domain>
## Task Boundary

Quand une session est publiée sur un spot, envoyer une push notification aux utilisateurs qui ont ce spot en favori. Ajouter également un système de préférences de notifications dans les réglages, et empêcher la création d'une session en doublon le même jour sur le même spot (proposer de rejoindre à la place).

</domain>

<decisions>
## Implementation Decisions

### Ciblage des destinataires
- **Favoris uniquement** pour ce MVP. Le "top 1 spot le plus proche" est différé à une itération future.
- L'Edge Function `notify-session-created` existe déjà et implémente déjà ce ciblage par favoris.
- Ce qui manque : le webhook Supabase qui déclenche la fonction sur INSERT dans la table `sessions`.

### Infrastructure Edge Function
- L'Edge Function `notify-session-created` est déjà déployée et fonctionnelle (Phase 04).
- Il faut créer le **Database Webhook Supabase** (trigger pg_net sur INSERT sessions → appel HTTP vers l'Edge Function).
- Pattern : migration SQL commentée (comme Phase 04 pg_cron) avec instructions pour activer dans le Dashboard.

### Préférences de notification (UI)
- Ajouter une section "Notifications" dans l'onglet Profil (settings).
- Deux toggles MVP : "Notifications de session" (on/off global), "Spots en favoris" (sous-option).
- Stocker les préférences dans la table `profiles` (colonnes `notif_session_enabled BOOLEAN DEFAULT true`).
- L'Edge Function doit respecter ces préférences : filtrer les users qui ont `notif_session_enabled = false`.

### Conflit de session
- Bloquer la création si une session existe **déjà le même jour** sur le même spot.
- Logique dans `SessionsContext.createSession` : query `sessions` table avant INSERT.
- UX : afficher un message dans `SessionForm` avec un bouton "Rejoindre la session existante".
- Fenêtre de conflit : même `spot_id`, même jour calendaire (UTC).

### Claude's Discretion
- Format de la date dans le message de conflit (locale FR vs date brute)
- Design exact de la section notifications dans le Profil (position relative aux autres sections)
- Wording exact des notifications push (déjà en anglais dans l'Edge Function existante — laisser tel quel ou franciser selon CLAUDE.md)

</decisions>

<specifics>
## Specific Ideas

- La migration webhook doit utiliser `pg_net` ou un trigger Postgres → `supabase_functions.http_request()` si disponible. Pattern identique à la migration `002_notification_triggers.sql` (commenté, à activer manuellement).
- La colonne `notif_session_enabled` sur `profiles` doit avoir `DEFAULT true` pour ne pas casser les users existants.
- L'Edge Function doit être mise à jour pour joindre `profiles` et filtrer `notif_session_enabled = false` avant d'envoyer les tokens.
- Le check de conflit dans `createSession` : `SELECT id, starts_at, creator_id FROM sessions WHERE spot_id = $1 AND DATE(starts_at) = DATE($2)`.

</specifics>
