Fait vérifié à consigner (corrige une hypothèse de RESEARCH.md, A7 / Open Q6) :
`cacheSpotImages()` ne vit PAS dans `src/lib/offline.ts` mais dans `src/utils/offline.ts`.
Il est appelé depuis `src/context/FavoritesContext.tsx:47` (boucle sur tous les spots
favoris au chargement) et `:93` (au toggle d'un favori). Il utilise `fetch(url, {mode:'cors'})`
puis `cache.put` dans le Cache API (`updock-images-v1`). Aucun service worker n'existe
dans le projet (`grep -rn "serviceWorker" src/ index.html vite.config.ts` = 0 résultat),
donc ce cache n'est JAMAIS relu par les `<img>` : ce sont des requêtes réseau
**supplémentaires**, d'`initiatorType` `fetch` et non `img`.
=> Conséquence de mesure : filtrer sur `initiatorType === 'img'` neutralise le biais.
Le filtre « Img » de l'onglet Network de Chrome, lui, peut les inclure (classement par
type de contenu) — préférer l'instrumentation `performance.getEntriesByType('resource')`.

Instrument scriptable de comptage (à exécuter dans la console / via chrome-devtools-mcp) :
  performance.getEntriesByType('resource').filter(r => r.initiatorType === 'img').length
Relevé avant l'interaction, puis 2 s après — la différence est le compte.

Audit DOM (métrique C) :
  document.querySelectorAll('img[loading="lazy"]').length
